## Repairs

The shortcode previously requested `/js/peanut-forms.min.js` and
`/css/peanut-forms.min.css` on Hub. Neither exists in Hub main. Connect now ships
`assets/js/forms.js` and `assets/css/forms.css`, renders a restricted inert JSON
schema from the synchronized definition, and submits through the local WordPress
proxy. No Hub credential or private synchronized settings are emitted.

No visitor or session ID is baked into HTML. The browser creates a random session
per form instance. The proxy sets the top-level visitor ID from the submitting
request's 32-hex `peanut_vid` cookie, or removes it for an absent/invalid cookie.
The renderer never sends a visitor ID. A fresh uncached admin-ajax nonce request
handles both anonymous and logged-in browsers even after a page cache replay.

Hub accepted these IDs but `createSubmission()` discarded them. The paired fix
persists a narrow metadata subset, attributes agency-wide submissions to the
server-authenticated site, and links an existing Visitor only within that site.
When tracker sync has not created a Visitor row yet, the relation stays null and
the raw cookie ID is preserved in metadata. This does not invent or identify a
visitor from form email, and does not implement delayed relation reconciliation.

## Installed-site evidence

A disposable WordPress with Connect activated at localhost:8899 synchronized an
actual contact form from a running Hub instance at localhost:8898. Hub used the
#1753 dependency checkout plus the identity fix and a separate MariaDB test DB.
The real HTTP path was browser → WordPress proxy → authenticated Hub API → stored
FormSubmission. No Hub submission response was mocked.

Playwright fetched the WordPress-generated page once and replayed those exact
HTML bytes into two independent browser contexts. Both rendered Name/Email and
submitted successfully. The requests contained distinct random session IDs and
no visitor ID. The Hub records preserved respectively `aaaa…` and `bbbb…` from
the request cookies, with each browser's corresponding session ID. The browser
reported no JavaScript errors. This replay simulates a shared HTML cache; it does
not exercise a specific installed caching plugin, CDN, or production site.

Reproduce the browser test on a disposable synchronized contact form with slug
`cache-isolation-test`, Name/Email fields, button `Send`, and success message
`Validation submission received.`. With Playwright available in NODE_PATH, run:

```sh
PEANUT_FORMS_TEST_URL='http://localhost:8899/?page_id=4' \
  node scripts/tests/installed-hub-form.cjs
```

The test creates two real submissions. It saves response UUIDs, sessions and
synthetic cookie IDs in `/tmp/peanut-forms-browser-results.json`; verify those
UUIDs in Hub's database, as browser success alone cannot prove persisted identity.
Set PEANUT_FORMS_EVIDENCE_DIR to retain screenshots/results elsewhere.

## Scope and release gate

Standard fields and multi-step forms are supported. Enrollment, scheduling,
file uploads, signatures, address/name composites, rating/slider and conditional
logic require their dedicated flows and deliberately do not submit partial forms.
HTML field content is displayed as text, never executed. Analytics view/start/
abandon event forwarding is not implemented by this renderer.

3.41.0 is not ready to publish until the Hub dependency chain and these PRs pass
required checks and merge, Hub is deployed, and a representative installed site
passes render/submit and two-browser cached-page tests. Bump all authoritative
version declarations together at packaging time. Resynchronize forms and purge
WordPress/CDN page caches during rollout: old HTML still references missing assets
and may still contain old IDs/nonces. No production deployment, release artifact,
update-server change or existing customer-site verification occurred in this task.
