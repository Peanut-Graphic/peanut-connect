01 — The shape of the system

Execution at the edge.
Authoring in the Hub.

The plugin is the only thing that can touch the WordPress site directly — render a page, serve a popup, run an update. The Hub is where campaigns get authored and cross-site data is aggregated. The plugin must keep working with sane local defaults even when the Hub is absent. That asymmetry is the whole design — and the whole attack surface.

Rule 1 · Edge does execution

No synchronous Hub call ever sits in a page-render path. The moat is that the plugin can do what the Hub can't.

Rule 2 · Degrade to less-rich, never broken

If a feature breaks without the Hub instead of merely losing richness, it was designed wrong.

Rule 3 · Hub-blind by default

For sensitive clients the plugin must not leak the Hub's existence — no call-home, no URLs, no key in the page.

Rule 4 · Pre-fetch, don't block

Real-time decisioning is cached at the edge and refreshed on a schedule — never a live Hub call mid-request.

02 — How a Hub command is secured

Five gates between a command and the site

Every inbound Hub → Edge request to a /hub/* endpoint passes through the same sequence. Fail any gate and the request stops — fail-closed, with a clear status, never a silent success.

1 · Rate limit

per-site bucket

Keyed by validated site, not raw IP, so shared-host siblings don't starve each other. Runs before any auth work.

2 · HMAC signature + anti-replay

key never on the wire

The preferred path: an HMAC-SHA256 signature over method + route + timestamp + body, proving possession of the shared key without transmitting it. A fresh timestamp window and a single-use nonce, burned atomically, make a captured request non-replayable. (A static Bearer remains as a fallback for un-migrated sites.)

3 · Permission gate

close-default

One canonical permission set. High-impact powers — remote updates, content publishing, restore, the outbound proxy — default OFF. The owner opts in; a freshly paired site can monitor but not mutate.

4 · Destructive-op allowlist

3.12.0

Even with a valid key, the Hub can't deactivate or delete a security plugin (Wordfence, Sucuri, …), can't retarget a restore URL off-Hub, and can't overwrite an arbitrary post type. The blast radius of a leaked key is bounded by code, not trust.

5 · Execute + audit

activity log

The action runs and is recorded with the correct type/status/message — backups, restores and updates now actually appear in the audit trail (they previously threw and logged nothing).

03 — What was brought together

Eleven defenses, one hardened agent

No single fix mattered most — the point is the layering. A leaked key, a compromised Hub, a hostile visitor, a poisoned update server: each now meets a different wall.

Encryption at rest

The Hub key is sealed with libsodium under a key derived from the site's wp-config salts — off-database. A stolen DB dump yields ciphertext, not a credential.

A5 · v3.13.0

HMAC signing + anti-replay

Signed requests keep the key off the wire; an atomic single-use nonce closes the replay race that two concurrent requests could once slip through.

3.12.0

Bearer leak closed

Form pages no longer print the Hub key into HTML. Submissions route through a server-side edge proxy — the credential never reaches a visitor's view-source.

04 — How the key vault works

The key that can't be stolen by reading the database

The Hub key is also the HMAC signing secret, so it can't simply be hashed — it has to be recoverable. The answer is encryption with a key that lives outside the database, in the site's wp-config.php salts.

At rest in wp_options

enc:v1:base64( nonce · authenticated ciphertext )
  • Decrypt-on-use. The raw key is recovered only in memory to sign a request, then wiped (sodium_memzero).
  • Migrates itself. An existing plaintext key is returned once, then transparently re-stored encrypted on first read.
  • Fails closed. If salts rotate and the key can't be decrypted, the site behaves as un-paired — never a fatal error.
  • One door. Every read/write flows through a single accessor — proven by grep that nothing else touches the option.

06 — Honest state

What's deliberately not done

Honest state beats flattering state. One item remains — and it's an operations decision, not a code gap.

Deferred · verified, not punted

Require signed requests by default

The Hub already signs every command (confirmed on the Hub side). But flipping the edge to reject unsigned requests is sequence-sensitive: every production Hub must be confirmed signing before any site enforces it, or fleet monitoring breaks the moment a site upgrades. So it ships as a per-site enablement once the fleet is verified — not a blind default flip in a release. The switch exists today; turning it on is a rollout, not a patch.
